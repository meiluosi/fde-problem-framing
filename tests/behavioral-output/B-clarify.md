# 任务B：开始澄清客服需求

建议结论：Investigate；本轮进入需求澄清，不承诺建设范围。

原话（S1/B）：“客服太慢要AI”。想买的是AI；期望变化暂理解为缩短客户获得有效解决的时间（假设）；具体受损人群、慢的指标和成本未知。提出者身份未知；可能使用者为客服，受影响者包括客户与后续处理岗位，决策者待确认。

可直接向客户提出三个问题：
1. 最近一次您觉得“太慢”的请求，从提出到解决发生了什么，能提供脱敏时间记录吗？这会区分首次响应、排队等待与实际解决慢，决定先改哪个环节。
2. 三个月后算成功时，哪类客户的哪类请求会有什么可观察变化？谁使用工具、谁确认成功？请带一份现有指标报表或工单字段示例，避免以“上线AI”替代验收。
3. 同一类请求中，有没有解决很快的例子？请各取一例慢和快的脱敏工单及交接记录；比较知识查找、人员排班、权限与跨部门等待，决定AI是否能影响主要耗时。

候选业务问题：某类请求在某环节耗时过长，导致某类用户承担可观察损失；所有空缺待客户回答。竞争假设H1为客服找答案慢，H2为排队/授权/交接等待长，H3为信息不全导致返工。当前无证据支持排序；若主要耗时都在客服之外等待，会推翻“生成答案即可显著提速”的解释。

最小下一步：建议客服运营负责人提供一组可比较的快慢工单时间线和实际处理者说明，先查机制，再决定采样扩大或选定干预；不把两例视为总体证明。责任人与期限待确认。收到记录后重评；没有记录时可前瞻记录，不能声称现场诊断完成。

证据台账：E1=客户提出上述原话，状态为陈述事实，来源S1/B；单位/分母/窗口/采集方法均未知，限制为单句摘要，关联H1—H3，建议客服运营负责人提供脱敏工单。I1=期望缩短解决时间为假设，需客户确认。未能验证慢的存在与程度、根因、工作量、损失、AI适用性或任何收益；未编造客户回答。
